## Алхам 3: SLO хүснэгт

| Сценарио | SLI | Босго | Цонх |
| --- | --- | --- | --- |
| Гүйцэтгэл | /cart/add-ийн хариу хугацаа | p95<20мс, p99<100мс | 20 VU, 1 мин |
| Найдвартай ажиллагаа | /pay-ийн алдааны хувь | <8% | 20 VU, 1 мин |
| Хүртээмж | checks (амжилтын хувь) | ≥90% | 20 VU, 2 мин, 10с зогсолт |
| /report-ын хариу хугацаа (4-р) | /report-ын хариу хугацаа | p95<450мс | 20 VU, 1 мин |

Босго яагаад ингэж сонгосон: localhost дээр `/cart/add`-ийн бодит p95 нь 8.15мс, хамгийн удаан хүсэлт (max) 63.68мс гарсан тул зааврын жишээ 200мс огт утгагүй сул босго болно. p95-ийг 20мс (~2.5 дахин нөөцтэй), p99-ийг 100мс болгосон нь хэмжсэн max-аас ~1.5 дахин их — сэлгэн ажиллагаанаас (garbage collection) болох саатлыг дийлэнхдээ тэсвэрлэх боловч чанга хэвээр байхаар сонгосон. Найдвартай ажиллагааны сценариод серверт зориудаар 5% алдаа суулгасан, хэмжсэн утга 5.01% гарсан тул 8%-ийг бодит хэлбэлзлийг тэсвэрлэх боловч жинхэнэ доройтлыг барих хэмжээгээр авсан. Хүртээмж 90% гэдгийг доор алдааны нөөцөөр тайлбарлав. /report-ын 450мс нь сервер бодитоор 200-400мс хүлээдэг (хэмжсэн p95=402.31мс) тул ~12% нөөцтэй байхаар авсан.

Алдааны нөөц: 2 минутын цонхонд 90% гэдэг нь 120с × 10% = 12 секундийн эвдрэх эрх гэсэн үг. Бодит зогсолт ~10с байсан тул цагаар нөөц хэтрээгүй (10/12 ≈ 83%). Доор Алхам 5-д үүнийг хүсэлтээр дахин тооцно.

slo-test.js доторх threshold дээрх хүснэгттэй яг ижил:
```js
'http_req_duration{name:cart}':   ['p(95)<20', 'p(99)<100'],
'http_req_failed{name:pay}':      ['rate<0.08'],
'checks':                         ['rate>0.90'],
'http_req_duration{name:report}': ['p(95)<450'],
```

## Алхам 5: Гэнэтийн эвдрэлийн туршилт

`chaos.sh`-ийг ажиллуулж (2 минутын тестийг 40-р секундэд сервер зогсоож 10с дараа асаах) `results/chaos.txt` гаргасан. Терминалын логоор зогсолт 08:36:37-08:36:47 буюу ~10 секунд байсан, дахин асмагц хүсэлтүүд шууд амжилттай болсон.

Үр дүн: checks 87.76% (тэнцээгүй, шаардлага >90%), pay-ийн алдааны хувь 15.35% (тэнцээгүй, шаардлага <8%), cart болон report threshold тэнцсэн хэвээр.

Бодит хүртээмжийг хүсэлтээр (амжилттай хүсэлт / нийт хүсэлт) тооцвол: 5008/5706 = 87.76%. Энэ нь цагаар тооцсон 91.7%-аас (110с/120с) багасай гарсан.

Яагаад зөрөв: сервер унасан үед хүсэлт connection refused-ээр агшин зуур буцдаг тул VU нэг секундэд илүү олон хүсэлт илгээдэг болдог. Тиймээс зогсолтын нэг секунд хэвийн секундээс илүү олон хүсэлт "иддэг" болохоор хүсэлтээр тооцсон хүртээмж цагаар тооцсоноос муу гарна. Хүсэлтээр 90%-ийн SLO хангахын тулд зогсолт ~9.5 секундээс богино байх ёстой байсан (570.6 алдаатай хүсэлтийн нөөц байсан, 610 алдаа гарсан — хэтэрсэн).

Найдвартай ажиллагааны threshold (pay) мөн тэнцээгүй болсон, учир нь сервер унасан үед /pay-ийн хүсэлт бүр л амжилтгүй болдог — нэг эвдрэл хоёр SLO-г зэрэг зөрчсөн. Үүнийг тусгаарлахын тулд хүртээмжийн SLI-г "холболт амжилттай тогтсон эсэх", найдвартай ажиллагааны SLI-г "холбогдсон хүсэлтүүдийн дотор 500 буцсан хувь" гэж тусад нь тодорхойлж болно — ингэвэл эвдрэл зөвхөн хүртээмжид, төлбөрийн системийн 5%-ийн алдаа зөвхөн найдвартай ажиллагааны хэмжүүрт тусна.

## Алхам 6: Threshold-оо зориуд эвдэх

`slo-test-fail.js`-д /report threshold-ыг p(95)<100 болгосон (сервер 200мс-аас хурдан хариулдаггүй тул баттай тэнцээгүй болно), /cart/add-ыг p(95)<50 болгосон (localhost дээр энэ нь бодит p95-ээс хол тул тэнцсэн хэвээр үлдэнэ).

```bash
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt
echo "exit=${PIPESTATUS[0]}" | tee results/fail-exit-code.txt
```

results/fail.txt: report threshold тэнцээгүй (p95=400.57мс > 100), бусад бүгд тэнцсэн. k6-ийн жинхэнэ exit code 99 гарсан (results/fail-exit-code.txt) — CI яг энэ кодоор build зогсооно. Анхаарах зүйл: `tee` ашигласан pipeline дээр энгийн `echo $?` нь k6-ийн код биш tee-гийн (0) кодыг харуулдаг тул `${PIPESTATUS[0]}`-ыг ашигласан.

## Дүгнэлт

Сценарио бичихээс SLO гаргах нь харьцангуй амархан байсан ч SLO-г бодит k6 threshold болгоход хамгийн хэцүү зүйл нь босгын тоог таамгаар биш бодитоор сонгох байлаа. Анхны 200мс жишээ localhost дээрх бодит хэмжилттэй харьцуулахад юу ч хэмжихгүй сул тул чангаруулах шаардлагатай болсон; анхны 10мс/50мс threshold ч миний машин дээр өөр ачаалалтай тохиолдолд тэнцээгүй болсныг үзээд 20мс/100мс болгож нөөцтэй болгосон. Гэнэтийн эвдрэлийн туршилт нь миний хүртээмжийн сценариог хэсэгчлэн үгүйсгэсэн: цагаар тооцвол SLO хангагдсан (91.7%), харин хүсэлтээр тооцвол тэнцээгүй (87.76%) болсон, учир нь зогсолтын үед хүсэлт хурдан алдаж секундэд илүү олныг "идсэн". Энэ нь SLO-г цагаар тодорхойлохоо эсвэл хүсэлтээр тодорхойлохоо сценарио дээрээ тодорхой заах хэрэгтэйг харууллаа. Нэг эвдрэл хоёр SLO (хүртээмж, найдвартай ажиллагаа)-г зэрэг зөрчсөн нь SLI-үүдийг тусгаарлаж тодорхойлох шаардлагатайг ойлгуулсан. Алдааны нөөц цагаар 83% зарцуулагдсан ч хүсэлтээр 107% болсон нь тооцооны нэгж чухал болохыг харуулав. Зориуд тэнцээгүй болгосон тест k6-ийн exit code (99)-оор CI pipeline-ыг хэрхэн зогсоохыг тодорхой харуулсан.
