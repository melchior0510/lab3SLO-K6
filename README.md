## Алхам 3: SLO хүснэгт

| Сценарио | SLI | Босго | Цонх |
| --- | --- | --- | --- |
| Гүйцэтгэл | /cart/add-ийн хариу хугацаа | p95<20мс, p99<100мс | 20 VU, 1 мин |
| Найдвартай ажиллагаа | /pay-ийн алдааны хувь | <8% | 20 VU, 1 мин |
| Хүртээмж | checks (амжилтын хувь) | ≥90% | 20 VU, 2 мин, 10с зогсолт |
| /report-ын хариу хугацаа (4-р) | /report-ын хариу хугацаа | p95<450мс | 20 VU, 1 мин |

Босго яагаад ингэж сонгосон: localhost дээр `/cart/add`-ийн бодит p95 нь 8.15мс, хамгийн удаан хүсэлт (max) 63.68мс гарсан тул зааврын жишээ 200мс огт утгагүй сул босго болно. p95-ийг 20мс (~2.5 дахин нөөцтэй), p99-ийг 100мс болгосон нь хэмжсэн max-аас ~1.5 дахин их — сэлгэн ажиллагаанаас (garbage collection) болох саатлыг дийлэнхдээ тэсвэрлэх боловч чанга хэвээр байхаар сонгосон. Найдвартай ажиллагааны сценариод серверт зориудаар 5% алдаа суулгасан, хэмжсэн утга 5.01% гарсан тул 8%-ийг бодит хэлбэлзлийг тэсвэрлэх боловч жинхэнэ доройтлыг барих хэмжээгээр авсан. Хүртээмж 90% гэдгийг доор алдааны нөөцөөр тайлбарлав. /report-ын 450мс нь сервер бодитоор 200-400мс хүлээдэг (хэмжсэн p95=402.31мс) тул ~12% нөөцтэй байхаар авсан.

Алдааны нөөц: 2 минутын цонхонд 90% гэдэг нь 120с × 10% = 12 секундийн эвдрэх эрх гэсэн үг. Бодит зогсолт ~10с байсан тул цагаар нөөц хэтрээгүй (10/12 ≈ 83%). Доор Алхам 5-д үүнийг хүсэлтээр дахин тооцно.

slo-test.js доторх threshold дээрх хүснэгттэй яг ижил:
```js
'http_req_duration{name:cart}':   ['p(95)<20', 'p(99)<100'],
'http_req_failed{name:pay}':      ['rate<0.08'],
'checks':                         ['rate>0.90'],
'http_req_duration{name:report}': ['p(95)<450'],
```

## Алхам 5: Гэнэтийн эвдрэлийн туршилт

`chaos.sh`-ийг ажиллуулж (2 минутын тестийг 40-р секундэд сервер зогсоож 10с дараа асаах) `results/chaos.txt` гаргасан. Терминалын мөрөөр `server killed: 06:24:24`, `server restarted: 06:24:34` буюу зогсолт яг 10 секунд үргэлжилсэн. k6-ийн `Request Failed` логийн эхний ба сүүлийн мөр мөн 06:24:24, 06:24:34 байсан тул дахин асмагц хүсэлтүүд шууд амжилттай болсон (сэргэх хугацаа ≤ 15с ✓). k6 exit code = 99.

Threshold-ийн үр дүн (results/chaos.txt):
- checks (хүртээмж): 87.92% (4935/5613), шаардлага >90% — тэнцээгүй
- pay-ийн алдааны хувь: 15.12% (283/1871), шаардлага <8% — тэнцээгүй
- cart: p95=6.08мс (<20), p99=20.26мс (<100) — тэнцсэн
- report: p95=397.3мс (<450) — тэнцсэн

Бодит хүртээмжийг хүсэлтээр (амжилттай хүсэлт / нийт хүсэлт) тооцвол 4935/5613 = 87.92%. Зөвхөн зогсолтоос болсон алдааг (595 `Request Failed`) авбал (5613 − 595)/5613 = 89.40%. Цагаар тооцвол 110с/120с = 91.7%.

Алдааны нөөц (хүсэлтээр): 10% × 5613 = 561.3 алдаатай хүсэлт. Зогсолтоос 595 алдаа гарсан (561.3-ын 106%), бүх алдаатай нийлбэл 678 (121%) тул хоёуланд нь нөөц хэтэрсэн. Цагаар харвал 10с нь 12с-ийн нөөцийн 83% тул хэтрээгүй.

Яагаад цаг ба хүсэлтийн тооцоо зөрөв: сервер унасан үед хүсэлт connection refused-ээр шууд буцдаг тул VU-ууд секундэд ~59.5 хүсэлт (595/10с) илгээсэн. Хэвийн үед ~45 хүсэлт/с (pass.txt: 44.87/с) байдаг, учир нь /report-ын 200-400мс хүлээлт нэг давталтыг удаашруулдаг. Тиймээс зогсолтын нэг секунд хэвийн секундээс ~1.3 дахин олон хүсэлтийг "иддэг" бөгөөд хүсэлтээр тооцсон хүртээмж цагаар тооцсоноос муу гарна. Хүсэлтээр 90%-ийн SLO хангахын тулд зогсолт 561.3 / 59.5 ≈ 9.4 секундээс богино байх ёстой байсан.

Найдвартай ажиллагааны threshold (pay) мөн тэнцээгүй болсон (15.12%). Нийт 678 алдаанаас 595 нь зогсолтын (холболтын) алдаа, үлдсэн 678 − 595 = 83 нь /pay-ийн 500 алдаа. Тэгвэл pay-ийн 283 алдаанаас зогсолтоос болсон нь 283 − 83 = 200. Хэрэв 83 алдааг зогсолтгүй үеийн /pay хүсэлтэд (1871 − 200 = 1671) харьцуулбал 4.97% буюу серверт суулгасан ~5%-тай таарч байна. Нэг эвдрэл хоёр SLO-г зэрэг зөрчсөн тул SLI-г тусгаарлах хэрэгтэй: хүртээмжийн SLI-г "холболт амжилттай тогтсон эсэх", найдвартай ажиллагааны SLI-г "холбогдсон хүсэлтүүдийн дотор 500 буцсан хувь" гэж тодорхойлбол эвдрэл зөвхөн хүртээмжид, төлбөрийн системийн 5%-ийн алдаа зөвхөн найдвартай ажиллагаанд тусна.

## Алхам 6: Threshold-оо зориуд эвдэх

`slo-test-fail.js`-д /report threshold-ыг p(95)<100 болгосон (сервер 200мс-аас хурдан хариулдаггүй тул баттай тэнцээгүй болно), /cart/add-ыг p(95)<50 болгосон (localhost дээр энэ нь бодит p95-ээс хол тул тэнцсэн хэвээр үлдэнэ).

```bash
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt
echo "exit=${PIPESTATUS[0]}" | tee results/fail-exit-code.txt
```

results/fail.txt: report threshold тэнцээгүй (p95=400.57мс > 100), бусад бүгд тэнцсэн. k6-ийн жинхэнэ exit code 99 гарсан (results/fail-exit-code.txt) — CI яг энэ кодоор build зогсооно. Анхаарах зүйл: `tee` ашигласан pipeline дээр энгийн `echo $?` нь k6-ийн код биш tee-гийн (0) кодыг харуулдаг тул `${PIPESTATUS[0]}`-ыг ашигласан.

## Дүгнэлт

Сценарио бичихээс SLO гаргах нь харьцангуй амархан байсан ч SLO-г бодит k6 threshold болгоход хамгийн хэцүү нь босгын тоог таамгаар биш бодитоор сонгох байлаа. Анхны 10мс/50мс босго миний машин дээр тэнцээгүй гарсан тул өөрийн хэмжилтээр (p95=8.15мс, max=63.68мс) 20мс/100мс болгож тохируулсан. Гэнэтийн эвдрэлийн туршилт миний хүртээмжийн сценарийг хэсэгчлэн үгүйсгэсэн: цагаар тооцвол 91.7% боловч хүсэлтээр тооцвол 87.92% болж тэнцээгүй. Шалтгаан нь зогсолтын үед хүсэлт шууд алдаж, секундэд ~59.5 хүсэлт (хэвийн үед ~45) "идсэн" явдал юм. Иймд SLO-г цагаар эсвэл хүсэлтээр тодорхойлохоо сценарио дээрээ заавал заах хэрэгтэйг ойлгосон. Алдааны нөөц цагаар 83% зарцуулагдсан ч хүсэлтээр 106% болж хэтэрсэн нь тооцооны нэгж чухал болохыг харуулав. Нэг эвдрэл хоёр SLO (хүртээмж, найдвартай ажиллагаа)-г зэрэг зөрчиж pay 15.12% болсон нь SLI-үүдийг тусгаарлаж тодорхойлох шаардлагатайг ойлгуулсан. Зориуд тэнцээгүй болгосон тест k6-ийн exit code 99 буцааж CI pipeline-ыг хэрхэн зогсоохыг харуулсан. Мөн README-ийн тоо бүр results/ доторх файлаас гарсан байх ёстой, туршилтыг өөрийн машин дээр бүтнээр нь ажиллуулах ёстой гэдгийг практикаар мэдэрсэн.
